# 641: Qwen3.5-4B, LoRA только для класса

Статус: **новая цепочка быстрых ядер закрыта; legacy-eager технический smoke
успешен, полные folds 0/3 запущены на новых проверенных preset**.

## Почему прежние Qwen3.5-4B обучались, а этот запуск пока падал

Это не новая и не доказанно более тяжёлая модель. Эксперименты `190`, `230`,
`260` и `600` уже успешно обучали тот же `Qwen3.5-4B` с rsLoRA rank `16` по
проекциям `q/k/v/o`, длиной `1536`, eager attention и gradient checkpointing.
Следовательно, обучаемость 4B и достаточность одной H100 уже подтверждены.

Разница находится в операционном контракте новой сетки. Старый runner полагался
на заранее собранное окружение и не фиксировал в артефакте точные версии всего
стека линейного внимания. Новый runner закрепляет revision модели,
Transformers/PEFT и каждую библиотеку быстрого Gated DeltaNet, а затем выполняет
настоящий forward/backward до допуска основного обучения. Именно здесь
последовательно обнаружились отсутствующие или несовместимые бинарные
зависимости. Без них Transformers молча выбирал памятьёмкую реализацию на чистом
PyTorch и получал OOM. Это инфраструктурная регрессия новой воспроизводимой
среды, а не отрицательный результат class-only LoRA. До первого optimizer step
ни одна из этих попыток не дошла, поэтому они не входят в научное сравнение.

Точную версию старого окружения восстановить из адаптеров нельзя: исторический
train report её не сохранял. Поэтому нельзя честно утверждать, что проблема
вызвана одной конкретной версией пакета; подтверждена только цепочка перехода в
fallback и её технические причины.

Первый запуск дошёл до forward и подтвердил OOM в резервной PyTorch-реализации
линейного внимания. Первый технический повтор остановился до обучения из-за
несовместимой версии kernel-пакета. Следующий повтор установил совместимую
версию, но показал, что одного hub-kernel недостаточно на H100: без FLA и
causal-conv1d модель снова выбрала тяжёлый PyTorch fallback. Текущий preflight
закрепляет полный официальный fast path и проверяет его импорты до загрузки
модели; данные, модель, loss, seed, effective batch и порог не менялись.

Этот preflight обнаружил ещё одну точную причину: пакет
`flash-linear-attention==0.5.2` является оболочкой, а реализация `fla.ops`
поставляется отдельным `fla-core`. Импорт функций мог проходить за счёт старой
версии core в окружении, тогда как Transformers не признавал её быстрым путём.
Текущий повтор закрепляет согласованные `fla-core==0.5.2` и
`flash-linear-attention==0.5.2`, отключает неподходящую аппаратную Hub-подмену
и до загрузки весов проверяет, что четыре Qwen-обёртки действительно связаны с
FLA/causal-conv1d, а не с PyTorch fallback.

Первый запуск этого варианта остановился ещё до установки зависимостей: внешний
runtime-index временно перестал отдавать уже закреплённый Transformers 5.15.1.
Менять версию после фиксации сетки запрещено. Поэтому точный platform-independent
wheel доставляется внутри runtime, проверяется по SHA-256
`b7cdf238ff583e3a58dbc7fa34da1aaf091ce063141f65a30538160bd5afe93f` и только
затем устанавливается. Модельный код и зависимости остаются той же версии.

Следующий запуск подтвердил ещё один инфраструктурный блокер до обучения:
`causal-conv1d` попытался собрать CUDA-расширение из исходников, но в runtime
нет `nvcc`. Поэтому используется официальный готовый wheel ровно для
CPython 3.12, PyTorch 2.10, CUDA 12 и CXX11 ABI. Его SHA-256
`c16c1c48d4fa63415cc797e02d69f97248c57c04627d99e394d5bb0ef266e288`
проверяется до установки. Это меняет только способ доставки той же версии
`1.6.2.post1`, а не модель, данные или обучение.

Следующий preflight остановился ещё раньше импорта модели: при установке FLA с
`--no-deps` отсутствовал его обязательный `einops`. Теперь точные wheels
`fla-core==0.5.2`, `flash-linear-attention==0.5.2` и `einops==0.8.2` также
доставляются с контрольными суммами. Перед импортом FLA отдельно проверяются
CUDA и активный backend Triton `3.6.0`, чтобы предупреждение об откате на CPU
не могло пройти незамеченным.

Этот вариант дошёл до инициализации CUDA-backend и подтвердил последнюю
техническую причину: Triton компилирует небольшой загрузчик, а в runtime не
было C-компилятора. Новый preflight не загружает модель и данные. Он доставляет
самодостаточный `ziglang==0.16.0`, проверяет его wheel по SHA-256 и выполняет
на H100 настоящие forward/backward для `causal-conv1d` и FLA gated-delta-rule.
Полное обучение разрешено только после конечных выходов и градиентов обоих
ядер; проверка одних импортов больше не считается достаточной.

Повтор с корректным вызовом `zig cc/c++` подтвердил следующий конкретный
недостающий слой окружения: компилятор запущен, но Triton-загрузчик включает
`Python.h`, которого нет по объявленному runtime-пути заголовков CPython 3.12.
Задача завершилась до загрузки весов и до первого optimizer step. Следующий
допустимый повтор должен добавить точные заголовки CPython 3.12 и сначала
повторить тот же kernel-only forward/backward; менять модель или рецепт LoRA
для обхода этой ошибки нельзя.

Заголовки CPython 3.12 были успешно установлены в следующей проверке, после
чего проявился новый блокер линковки: компактный загрузчик Triton не смог найти
`libcuda.so.1`. Отдельный повтор с явным поиском библиотеки драйвера завершился
тем же способом. Обе задачи остановились до загрузки модели. После серии таких
сбоев продолжать собирать новый системный стек нецелесообразно и противоречит
заранее заданному ограничению проекта.

Поэтому научный контракт `641` не меняется, а меняется только способ исполнения:
следующая техническая проверка использует базовый образ и eager-загрузку,
которые уже успешно обучили ту же revision Qwen3.5-4B в `623` и `632`. Она не
устанавливает новые Transformers или CUDA-ядра. Технический smoke успешно
выполнил обучение и сохранение адаптера, дал `2/2` конечных score за `0,091`
минуты, не прочитал validation labels и подтвердил backend `legacy_eager`.
Архив целостен; SHA-256 внешнего ZIP:
`b00e719fe44d91ea96061187807bb5091a48ea2d04cb8c5ade40ec8a730c6f19`.
После этого созданы, проверены и запущены новые full-preset folds 0/3. Старые
fast-path preset остаются запрещёнными.

Это маленькая обученная ячейка честной сетки `размер × способ обучения`. Она
получает ровно тот же первый снимок, название, описание, правило, очистку текста
и atomic `0/1` prompt, что prompting-эксперимент `640`. Меняется только наличие
LoRA-обучения на донорских folds.

## Гипотеза и контроль

Контроль — `640/Qwen3.5-4B prompting`. Механизм: supervised LoRA должна изучить
локальную границу категорий без изменения входа или порога. Сравнение с `642`
измеряет только масштаб модели, а сравнение с `643` — только добавление
grounded-evidence auxiliary objective.

Используется рецепт hard selection исходного Qwen-компонента, но selection
физически выполняется до GPU только на четырёх donor folds. Validation JSONL не
содержит label или evidence target. Seed `42`, один epoch, effective batch `16`,
rsLoRA rank `16`, learning rate `2e-4`, порог `0`.

## Запуск

Сначала строится отдельный runtime для fold `0`, затем fold `3`:

```bash
python experiments/641_qwen35_4b_class_only_lora/build_runtime.py --help
python experiments/641_qwen35_4b_class_only_lora/run_fold.py --help
```

Пакет не содержит scheduler preset, URL, данные, веса или результаты. Folds
`1/2/4` разрешены только решением screen evaluator `645`.
