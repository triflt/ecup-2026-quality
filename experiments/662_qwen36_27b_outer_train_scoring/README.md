# 662: расчёт outer-train целей Qwen3.6-27B

Статус: **все пять полных folds приняты; target-set терминально собран**.

Первая попытка остановилась до загрузки модели: macOS добавил в транспортный
архив служебные файлы `._*`, и строгая проверка манифеста адаптера обнаружила
лишние элементы. Веса, runtime, строки и код расчёта не менялись. Архивы
пересобраны без служебных метаданных под новыми ключами, скачаны обратно и
побайтово сверены по SHA-256; повтор прошёл предварительную проверку запуска.
Повтор затем дал точные `8/8` строк, конечные raw logits, совпадение порядка
occurrences и нулевой доступ к validation, её меткам, Public и sealed данным.
Frozen audit сохранён в `results/smoke_acceptance_audit.json`. Первая полная
волна завершилась успешно: folds 0/1/3 дали соответственно
`4 892/4 894/4 892` строк, прошли внешний delivery-контракт, внутренний ZIP,
SHA, конечность logits и точную привязку occurrences. Их безопасные аудиты
сохранены в `results/fold{0,1,3}_acceptance_audit.json`; folds 0/3 сразу
переданы как входы screen-ветке 681. После освобождения слотов folds 2/4 были
рассчитаны второй волной по `4` GPU без изменения научного рецепта и также
приняты на `4 892/4 894` строках. Полный набор содержит `24 464` occurrences.
Фактическое end-to-end время пяти folds составило `32,67–40,97` минуты
(`1,99–2,50` строки/с), суммарно `12,37` GPU-часа; двухчасовой лимит
подтверждён с большим запасом.

Эксперимент не обучает модель и не является кандидатом на отправку. Для каждого
outer fold принятый адаптер 654 оценивает только те training occurrences, на
которых он был обучен. Результат — in-sample teacher targets для отдельного
эксперимента дистилляции, а не OOF-прогнозы и не честная validation-метрика.

Runtime создаётся из неизменяемого `train.jsonl`, но удаляет метки до сборки
GPU-bundle. `validation.jsonl`, registry, selector и исходный датасет в задачу
не передаются. Контракт фиксирует SHA source train, адаптера и упорядоченных
ключей `(global_index, id, category, fold, occurrence_index)`, запрещает строки
outer validation и требует конечный raw score `logit("1") - logit("0")` без
sigmoid, температуры, порога или калибровки.

Сначала fold 0 обязан дать `8/8` корректных строк. Только после проверки ZIP,
self-hash отчёта и точной привязки к runtime разрешён полный label-free scoring.
Эти ответы можно использовать только как train targets deployable student;
outer-fold validation не участвует в обучении или выборе.

Полные runtimes всех пяти folds уже собраны и прошли локальную проверку схемы,
контрольных сумм и точного порядка occurrences. Они не разрешают массовый
запуск сами по себе: сначала скачивается и принимается отдельный smoke-архив.

После приёмки всех пяти полных артефактов `verify_target_set.py` повторно
запускает построчный verifier для каждого ZIP и принимает только точный набор
folds `0..4`: `24 464` обучающих occurrences, пять различных outer-train и
runtime-контрактов, нулевое чтение validation, sealed и Public. Этот агрегатный
контракт проверяет готовность development-targets для полной CV эксперимента
681, но не разрешает финальный refit.

Причина сильнее простого отсутствия sealed-товаров. В CV teacher каждого fold
оценивает строки, на которых он сам обучался. Дешёвая замена для полного refit
из OOF-ответов пяти teacher-моделей является leakage-safe, но даёт материально
другие цели: на folds 0/1/3 средняя абсолютная разница logits равна
`1,908/1,358/1,406`, а число неоднозначных soft-targets при `T=2` возрастает
с `57/26/36` до `108/118/135`. Поэтому даже успешная CV 681 сама по себе не
открывает ни OOF full-refit, ни отдельный расчёт только недостающих sealed-строк.
Recipe-equivalent final refit требует отдельного заранее замороженного
контракта: full-data 27B teacher обучается на всём разрешённом train и затем
без меток оценивает те же train occurrences. Любая OOF-политика должна идти
как отдельная абляция с собственным ID и полной проверкой.
