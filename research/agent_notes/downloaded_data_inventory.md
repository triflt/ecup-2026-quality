- 1/2/3/4/5 изображений имеют соответственно
  1,800/1,153/1,460/1,820/6,738 товаров;
- суммарный исходный размер изображений: 9,580,433,869 байт;
- суммарный compressed size entries: 9,177,652,656 байт;
- архив не содержит ZIP comment;
- `unzip -t`: ошибок CRC/сжатия нет.

Эти значения точно совпадают с
`research/s3_image_sanity_detailed.json`: прежний аудит независимо получил
49,456 S3 image objects, 9,580,433,869 байт, те же 62,430 ZIP entries и нулевые
missing/extra/noncontiguous counts. Размер свежего ZIP также точно равен
записанному удалённому `zip_size_bytes=9,189,322,555`.

Контрольные суммы ZIP:

- SHA-256: `9ff051272e9ee1b08d6d05939470ebc7006403f4647c546b29647efb03837edc`;
- MD5: `3a708f5619cba7944ba114e0ef2c2d7a`.

MD5 большого архива нельзя автоматически считать S3 ETag: объект мог быть
загружен multipart-способом. Приоритетны `ChecksumSHA256`/пользовательская
metadata из `stat`, а при их отсутствии — SHA-256 повторного download.

### Дополнительный сигнал для нового family graph

По парам `(ZIP CRC32, uncompressed size)` найдено 6,982 content fingerprints,
повторяющихся между разными товарами; они затрагивают 7,084 строки. Это
структурный proxy, а не криптографическое доказательство равенства, но коллизии
такого масштаба показывают, что all-gallery graph должен проверять байты.

Максимальный fingerprint встречается у 236 товаров почти исключительно на
gallery positions 3/4. Следующий — у 144 товаров на вспомогательных позициях.
Есть также пять fingerprints, каждый общий для одних и тех же 84 flammable
товаров на positions 0–4. Это подтверждает риск: одно совпавшее вспомогательное
изображение может быть баннером/инструкцией, а не идентификатором товара. Нельзя
безусловно union-ить товары по одному arbitrary gallery image. Для окончательного
графа нужно потоково посчитать SHA-256 содержимого entries и применить правила
корроборации из `semantic_split_design_critique.md`.

## Какие S3 объекты проверять окончательно

Имя bucket и приватный префикс намеренно не публикуются.

### Обязательные `stat`

1. `private://competition-artifacts/data.csv`
   - ожидаемый `ContentLength`: 37,164,187;
   - если ETag single-part, ожидаемый MD5:
     `e39ff94c0d4c29a113b858b85b81ee58`;
   - сохранить `ETag`, `VersionId`, `LastModified`, `ChecksumSHA256` и metadata,
     если сервис их возвращает.
2. `private://competition-artifacts/images.zip`
   - ожидаемый `ContentLength`: 9,189,322,555;
   - сохранить `ETag`, multipart-признак, `VersionId`, `LastModified`,
     `ChecksumSHA256` и metadata;
   - не сравнивать multipart ETag с локальным MD5.

### Обязательный prefix-list, а не 49,456 отдельных downloads

`private://competition-artifacts/images/`

Нужно повторить `list_objects_v2` и проверить ожидаемые 49,456 image objects,
12,972 folder markers, два служебных объекта, суммарные image bytes
9,580,433,869 и точное множество ключей
`images/<id>/<index>.jpg` относительно ZIP. Для каждого image
object достаточно сохранить key/size/ETag/version metadata. Скачивать все
отдельные объекты не нужно, если canonical `images.zip` подтвердит SHA-256 и его
центральный каталог/CRC уже проверены.

### Когда нужен `download`

- Скачать канонический `data.csv` в **новый** временный путь и сравнить
  SHA-256, если `stat` не возвращает доверенный SHA-256 либо ETag multipart.
- Скачать канонический `images.zip` в **новый** временный путь и сравнить
  SHA-256 с `9ff051…37edc`, если `stat` не содержит совпадающий trusted checksum.
  Это единственный строгий способ доказать побайтовое равенство свежего локального
  архива и S3 canonical object при отсутствии checksum metadata.
- Никакой отдельный S3 key для `research/data.csv.gz` в текущих конфигурациях не
  найден: ML configs ссылаются на uncompressed
  канонический несжатый `data.csv`. Локальный gzip и три parts уже полностью
  сверены.

## Оставшиеся блокеры

1. В репозитории нет сохранённого SHA-256 удалённого `images.zip`; пока доказано
   структурное соответствие и точное совпадение размера, но не remote byte
   identity.
2. В S3-аудите не зафиксирован SHA/ETag `data.csv`; локальные копии между собой
   идентичны, remote identity требует `stat` или одного download.
3. `research/lora_image_manifest.tsv.gz` повреждён; это не влияет на полный
   manifest, но должно быть fail-closed в новых runners.
4. S3 во время этого задания намеренно не вызывался, поэтому текущие VersionId,
   LastModified, ETag и checksum metadata неизвестны.

Итого: свежий локальный dataset полный и внутренне согласованный; для закрытия
цепочки происхождения нужны только read-only `stat` двух canonical objects,
повторный list image prefix и, если S3 не отдаёт trusted checksum, download этих
двух canonical files в новые временные пути с SHA-256 проверкой.
