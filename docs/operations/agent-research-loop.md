# Управляемый цикл исследований с агентами

Обновлено: 2026-08-21. Подход основан на полезных идеях OpenRsi, но реализован самостоятельно под соревнование. Исходный код OpenRsi не копируется: в репозитории источника отсутствует файл лицензии.

## Зачем нужен этот порядок

Несколько агентов могут быстро породить десятки правдоподобных идей. Без общего порядка это приводит к повторению опытов, расходу GPU и выбору случайно удачного результата. Цикл ниже отделяет предложение идеи, проверку её смысла, запуск и признание нового лидера.

## Роли

1. **Исследователь** формулирует механизм, один изменяемый фактор, ожидаемый прирост и условие опровержения.
2. **Критик** проверяет журнал прошлых опытов, литературу, риск утечки, стоимость и возможность честного сравнения.
3. **Ответственный за проверку** заранее утверждает версии данных, разбиения, метрики и ограничения по категориям.
4. **Исполнитель** запускает только утверждённый опыт и не меняет правила принятия после получения результата.
5. **Интегратор** повторно проверяет победителя, обновляет общий журнал и единолично меняет `champion.json`.

Один агент может последовательно исполнять несколько ролей, но критика и финальная проверка не должны основываться только на самооценке автора гипотезы.

## Жизненный цикл гипотезы

1. Создать папку из `templates/experiment/` и заполнить `experiment.toml`.
2. Записать в нём механизм, baseline, единственный изменяемый фактор, gate и бюджет.
3. Провести предварительную проверку без GPU.
4. Утвердить или отклонить запуск с короткой причиной.
5. Выполнить минимальный опыт на одном заранее выбранном разбиении.
6. Только после прохождения первого барьера запустить все пять разбиений.
7. Повторить результат или оценить его неопределённость.
8. Проверить чистую сборку, время, память, формат и контрольные суммы.
9. Записать результат, включая отрицательный, в общий журнал.
10. Обновить текущего лидера только при выполнении всех условий принятия.

## Что считается доказательством

- улучшение Macro F1 относительно заранее указанного исходного решения;
- победа не менее чем на четырёх из пяти разбиений, если не обоснован другой критерий;
- отсутствие недопустимого падения одной категории;
- отсутствие передачи меток между обучением и проверкой;
- повторное получение результата;
- укладывание итогового решения в ограничения платформы.

Мнение агента, высокая общая метрика на прогнозах, одно удачное разбиение и последующая подгонка под Public не считаются достаточными доказательствами.

## Экономия ресурсов

GPU получают только гипотезы, которые:

- не повторяют отклонённый опыт;
- объясняют конкретный тип ошибок;
- изменяют одну основную часть решения;
- имеют дешёвую предварительную проверку;
- могут улучшить текущего лидера без нарушения времени применения.

Вычислительные часы и число планируемых отправок записываются до запуска. Public используется редко — для заранее зафиксированной архитектурной гипотезы.
